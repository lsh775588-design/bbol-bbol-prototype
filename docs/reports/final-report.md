## 2. 구현한 기능

### 서버 API (팀 저장소 스택, 14개)
| API | 하는 일 |
|---|---|
| `GET /health` | 서버 상태 확인(공개) |
| `POST /auth/signup` | 이메일 가입(HTTP 201). 닉네임 규칙(금칙어, 중복, 형식)과 이메일 인증 토큰 검증. 가입하면 access와 refresh 토큰 발급 |
| `POST /auth/login` | 로그인. 이메일 없음, 비밀번호 틀림, 탈퇴, 카카오 전용 계정이 모두 같은 응답(AUTH4011) |
| `GET /users/me` | 내 정보 |
| `PATCH /users/me` | 닉네임 변경(30일에 1번, 금칙어, 중복 검사) |
| `GET /auth/email-availability` | 이메일 중복 확인(공개) |
| `GET /auth/nickname-availability` | 닉네임 사용 가능 여부(공개) |
| `GET /place-categories` | 장소 카테고리 8개와 기본 점수 |
| `GET /places` | 내 주변 장소(반경, 카테고리 필터, 거리순). 인증 후 방문 여부와 오늘 완료 여부 반영 |
| `GET /places/{id}` | 장소 상세 |
| `GET /places/recommendations` | 뽈뽈 추천 장소(CURATED만). 안 가본 곳 우선 + 거리순 |
| `POST /places/{id}/completions` | 도착 인증(HTTP 201). 위치, 정확도, 모의 위치 검사, 하루 1회, 첫 방문 100%와 재방문 50% 포인트 |
| `GET /users/me/points` | 총 포인트, 오늘 포인트, 인증 횟수 |
| `GET /users/me/point-histories` | 포인트 적립 내역(커서 페이지네이션) |
| `GET /users/me/completions` | 활동 일지(기간과 카테고리 필터, 커서 페이지네이션) |

### 공통 기능(서버)
- 공통 응답 `{success, code, message, data}`, 명세의 에러 코드 체계, COMMON400의 필드별 오류(`data.errors`)
- 보안: JWT(access 1시간, refresh 14일), 공개 경로 설정, 토큰 없으면 AUTH401, 탈퇴 사용자의 토큰 차단
- 한국 시간(Asia/Seoul) 기준 `Clock`, 마이그레이션(Flyway), 로컬 개발용 고정 사용자 필터(local 전용)
- `local` 환경에서만 로드되는 샘플 데이터: 종로구 장소 33곳(뽈뽈 추천 13곳), 데모 계정 4개, 샘플 도착 기록

### 앱 화면
- 로그인, 회원가입(이메일과 닉네임 실시간 중복 확인), 홈(인사, 포인트 카드, 추천 카드, 최근 활동), 지도(OpenStreetMap, 위치 권한 설명, 둘러보기 모드, 카테고리 필터, 장소 상세, 도착 인증), 포인트 내역, 활동 일지, 뽈뽈 추천 목록, 마이(프로필, 통계 타일, 닉네임 변경, 로그아웃), 랭킹(준비 중 안내)
- 하단 탭 4개(홈, 지도, 랭킹, 마이), 프로토타입에 맞춘 보라색 디자인

### 개발 방식
- 오케스트레이터가 계획과 검증을 맡고, 역할별 에이전트(backend, db, app, test, review)에게 작업을 나눠 맡겼다. 에이전트는 별도 git worktree와 브랜치에서 병렬로 일했고, 결과를 제가 직접 다시 실행해 확인한 뒤 로컬 통합 브랜치에서 합쳤다.
- 단계마다 읽기 전용 review를 돌렸다(0단계와 2단계 조건부 통과, 지적 사항은 모두 수정).
- 환경 제약: Docker와 WSL 배포판이 없어 PostgreSQL, PostGIS, Redis를 실제로 돌리지 못했다.

## 5. 구현하지 않은 것(쟁점 대기)
지시한 "쟁점 2~8이 결정된 API만 구현" 원칙에 따라 아래 API 14개는 만들지 않았다. 쟁점별 제안 기본값은 검토 문서(https://claude.ai/artifact/UxFFkRTkXhS4NJd6JjtSCi)에 있다.
| API | 기다리는 결정 |
|---|---|
| `POST /auth/email-verifications`, `POST /auth/email-verifications/confirm`, `POST /auth/password-reset` | 쟁점 2: 인증 토큰을 추측 불가능한 난수로 바꾸고 Redis에서 조회 |
| `POST /auth/reissue`, `POST /auth/logout` | 쟁점 3: refresh 재발급 동시 요청 대책(클라이언트 직렬화 또는 서버 유예) |
| `DELETE /users/me` | 쟁점 4: 탈퇴 닉네임 처리(NULL로 비우고 응답에서 "탈퇴한 사용자"로 치환) |
| `POST /auth/kakao`, `GET /users/me/onboarding`, `PATCH /users/me/onboarding` | 쟁점 1과 5: 카카오 값과 닉네임 없는 사용자의 API 범위 |
| `POST /completions/{id}/photo` | 쟁점 8: 사진 URL 추측 방지와 EXIF 제거 |
| `GET /users/me/stats`, `GET /rankings/users`, `GET /rankings/places`, `GET /rankings/streaks` | 쟁점 6: 통계와 랭킹의 날짜 기준(포인트 적립 시각) |
쟁점 7(카테고리와 장소 점수 우선순위)은 "장소 점수가 카테고리 점수를 덮는다"로 가정해 구현에 반영했다. 위 결정 중 제안대로 진행해도 되는 것을 알려주시면 바로 구현할 수 있다.

## 6. 미검증
- **PostgreSQL 17과 PostGIS, Redis 실연동:** Docker가 없어 한 번도 실행하지 못했다. 마이그레이션은 H2(PostgreSQL 모드)에서만 실행했고, refresh token의 Redis 저장소는 모의 객체 단위 테스트만 했다. 하루 1회 제한의 유니크 위반 판별도 PostgreSQL 형태 메시지는 가짜 예외로만 확인했다.
- **카카오 수집 스크립트 실호출:** 키가 없다. 실제 응답 형식과 45개 상한 분할 동작은 첫 실행 때 확인해야 한다.
- **앱 2단계와 UI 개편 화면의 실제 모습:** 에뮬레이터 사용을 중단하라는 요청이 있어서 컴파일과 단위 테스트까지만 확인했다. 1단계 화면(로그인, 가입, 지도, 상세, 내 정보)은 에뮬레이터에서 실제 서버와 연결해 스크린샷으로 확인했다(`docs/screenshots/stage-1`). 새 서버(팀 저장소 스택)로 다시 연결해 확인하지는 못했다.
- **위치 권한과 모의 위치 판별의 실제 값**, 안드로이드 8~10 기기에서의 위치 취득.
- **팀 저장소에 올리는 것:** 하지 않았다.

## 7. 알아둘 점(보안과 운영)
- **앱이 보내는 위치, 정확도, 모의 위치 값을 서버가 그대로 믿는다.** 악의적인 클라이언트가 정확도 0과 장소 좌표를 보내면 어디서든 인증할 수 있고, 요청 횟수 제한과 불가능한 이동 검사도 없다. 명세 백엔드 참고에 "완벽한 방어는 아님"이라고 적혀 있어 명세 위반은 아니다.
- **H2가 배포 산출물에도 들어간다**(`runtimeOnly`). 배포 전에 로컬과 테스트 전용으로 분리해야 한다. `local` 설정(고정 JWT 키, 고정 사용자)도 배포 산출물에 포함되므로, 운영에서 `local` 프로파일이 켜지지 않게 막아야 한다.
- **팀 저장소에 올릴 때 팀에 알려야 할 변경:** Flyway 도입과 `ddl-auto` 기본값 변경, 새 `docs/` 폴더, H2 추가. 팀원 로컬 DB가 이미 `update`로 만들어져 있다면 초기화나 baseline 설정이 필요하다.
- 비밀값은 코드에 없다. 개발용 가짜 값(JWT 키, 인증 토큰, 데모 계정 비밀번호)만 `local`과 `test` 설정에 있다.
- 장소 좌표와 주소는 공개 지식 기반의 대략값(샘플)이고 일부는 실제 매장이 아니라 "샘플" 표시다. 팀 검토가 필요하다.
- 샘플 계정으로 확인할 때는 `docs/local-demo.md`(서버 복제본의 `docs/`)를 본다.

### 구현 중 확인한 주의점 (나중에 직접 만들 때 고려)
에이전트 보고, 계약 테스트, 보안 점검에서 모은 것이다. 각 항목은 "이 프로젝트에서 실제로 부딪힌 것" 또는 "코드를 읽어 확인한 것"이다. Docker가 없어서 PostgreSQL과 Redis에서만 드러나는 문제는 포함되지 않았다.

#### A. 도메인 사이를 잇는 일이 가장 빠뜨리기 쉽다
- **탈퇴 정리 리스너가 없었다(보안 점검 높음).** 탈퇴를 만든 쪽은 `UserWithdrawnEvent`만 발행했고, 이를 받아 사진과 위치를 지우는 일은 다른 도메인 담당의 몫으로 남았는데 아무도 만들지 않았다. 각자의 테스트는 자기 범위 안에서 통과했고, 코드 설명에는 "삭제한다"고 적혀 있었다. 이벤트를 발행하는 쪽과 받는 쪽을 같은 작업 단위에서 만들고, 끝에서 끝까지(탈퇴 후 사진 파일이 사라졌는지) 확인하는 테스트가 있어야 한다.
- **따로 개발한 브랜치는 합쳐야 문제가 드러난다.** 장소 테스트가 만든 토큰의 사용자가 DB에 없어서, 사용자 상태 확인이 들어오자 14개가 401로 실패했다. 온보딩 차단이 들어오자 계약 테스트의 사용자가 온보딩 전이라 도착 인증이 403이 되어 5개가 실패했다. 합친 뒤 전체 테스트가 필수다.
- **서버에 새 규칙이 생기면 앱에도 화면이 있어야 한다.** 온보딩 미완료자의 도착 인증을 막았는데 앱에 온보딩 화면이 없어서, 새로 가입한 사용자는 도착 인증을 할 수 없었다. 데모 계정만 온보딩이 완료돼 있어서 숨어 있었다.
- 같은 이름의 테스트 지원 파일을 두 에이전트가 따로 만들어 병합 충돌이 났다(내용은 같았다). 공용 지원 파일은 한 곳에서 먼저 만든다.
- 한 도메인이 다른 도메인의 저장소를 쓰지 못하게 하면, 그 도메인이 읽기 전용 서비스 파일을 새로 만들어 준다(`PlaceQueryService`, `UserQueryService`). 대신 랭킹처럼 여러 도메인을 합쳐야 하는 집계는 SQL 조인 대신 메모리에서 하게 된다.

#### B. 명세와 구현 사이
- 비밀번호 재설정의 `purpose`는 `SIGNUP`과 `PASSWORD_RESET`이다(지시문에 `RESET`이라고 잘못 적어도 서버가 기준이 되어야 한다).
- 온보딩 요청은 명세대로 `ageGroup`, `gender`, `interests`이고 닉네임은 카카오 첫 온보딩에서만 받는다. 서버는 닉네임이 필요한지 알려주지 않아 앱이 "카카오 가입자이고 온보딩 미완료"로 추정한다.
- 재방문 사진: 명세는 마감 없이 보너스 0점을 허용하는데 지시는 모든 기록에 1시간이었다. 명세를 따랐다. 지시와 명세가 다르면 명세 우선으로 두고 보고하게 하는 것이 안전했다.
- 명세에 없어 임의로 정한 것: 에러 메시지 문구(EMAIL4001/4002/429/502, AUTH4012, KAKAO401/502), 이메일 코드를 5번째로 틀렸을 때의 응답(EMAIL4002), 검사 순서(도착 인증, 사진), 랭킹 동점과 최소 횟수, 재방문의 0점 보너스를 내역으로 남길지. 명세에 없는 코드: AUTH429, COMPLETION4031.
- EMAIL429에는 쿨다운인지 하루 한도인지 구분과 남은 시간이 없어 앱이 60초라고 가정한다.
- 사진 주소는 명세 예시가 절대 URL인데 서버는 상대 경로를 준다. 앱이 서버 주소를 붙이고, 호스트가 다르면 토큰을 보내지 않는다.
- 명세는 HEIC를 허용하지만 서버의 이미지 라이브러리는 HEIC와 WebP를 읽지 못한다. 앱이 JPEG로 변환해서 보낸다(HEIC 디코드는 안드로이드 9 이상에서만 가능).
- 응답 `message` 문구, 열거형 값, 정수 폭은 계약 테스트에 넣지 않았다. 서버가 바꿔도 잡히지 않는다.

#### C. 인증과 토큰
- refresh token은 사용자당 1개이고 재발급마다 바뀐다. 서버가 옛 토큰을 20초 유예해서 동시 재발급이 둘 다 성공하지만, 그 유예에 기대면 앱의 중복 요청 버그가 가려진다. 앱은 옛 토큰을 두 번 보내지 않아야 한다.
- 유예는 한 칸이 아니라 체인이다(유예 안에서 재발급이 오면 그 시점의 현재 토큰도 20초 유예). 목록 상한이 10이면 동시 16개 테스트에서 옛 토큰이 밀려나서 50으로 올렸다.
- 앱 재발급은 "여러 요청이 동시에 401을 받을 때 재발급은 한 번만" 하도록 락 안에서 "실패한 요청의 토큰"과 "저장된 토큰"을 비교해야 한다. 이 비교가 없으면 재발급이 N번 나간다.
- 재발급이 네트워크 오류나 5xx로 실패했을 때 토큰을 지우면 오프라인에서 곧바로 로그아웃된다(제 첫 지시가 이랬다). 서버가 거절한 경우(408, 429 제외한 4xx)에만 지운다.
- 앱의 인증 인터셉터가 `auth/` 경로 전체에 토큰을 붙이지 않는데 `POST /auth/logout`은 인증이 필요하다. 로그아웃만 예외로 둬야 한다.
- access token은 서버에 상태가 없어서 로그아웃과 비밀번호 재설정 후에도 만료까지(1시간) 유효하다. 탈퇴만 매 요청 DB 확인으로 막는다.
- 실패 응답의 본문에 `data`가 없는 200(로그아웃, 탈퇴, 비밀번호 재설정)을 일반 응답 형식으로 읽으면 변환 오류가 나고, 그 오류는 네트워크 오류 처리에 잡히지 않는다.
- 로그인 시도 제한은 IP만 본다. 서버가 직접 본 주소만 쓰고(`X-Forwarded-For`를 믿으면 위조로 우회), 프록시 뒤에서는 모든 사용자가 한 IP로 보여 서로를 잠근다. 성공 로그인이 카운터를 초기화하므로 자기 계정이 있는 공격자가 다른 계정을 계속 시도할 수 있다. 계정별 카운터와 IPv6 /64 묶음이 필요하다.
- 로컬 개발용 고정 사용자 필터는 토큰이 없거나 탈퇴한 사용자의 요청도 사용자 1로 대체한다. 토큰 없는 `DELETE /users/me`가 데모 계정을 탈퇴시켰고, 탈퇴 후 401 확인이 가려졌다.

#### D. 이메일 인증과 가입
- 이메일 코드는 안전한 난수로 만들고 상수 시간으로 비교한다. 인증 토큰은 32바이트 난수이고 이메일과 용도에 묶이며 한 번만 쓰이고 저장소에는 해시만 둔다.
- 시도 횟수 확인이 코드 비교보다 늦으면 동시 요청으로 5회 제한을 넘겨 추측할 수 있다. 비교 전에 원자적으로 횟수를 선점해야 한다(보안 점검, 수정 중).
- 가입 용도의 코드 발송은 가입 여부를 숨길 수 없다(명세가 가입된 이메일이면 USER409를 요구). 반면 비밀번호 재설정은 가입 여부와 상관없이 같은 응답이어야 하는데, 실제 가입자에게만 메일이 동기로 발송돼서 응답 시간으로 구별된다. 비동기 발송이 필요하다.
- 발송 제한이 이메일 단위뿐이면 남의 주소로 메일 폭탄, 피해자의 하루 5회 소진(가입과 재설정 차단), 메일 서비스 한도 소진이 가능하다. IP별과 전역 제한이 필요하다.
- 쿨다운과 하루 횟수는 용도와 상관없이 이메일 하나에 걸어야 한다(용도별이면 같은 주소에 10통). "하루"는 한국 시간 달력 날짜 기준 고정 창이라 자정에 초기화된다.
- 가입은 "검증, 사용자 생성, 토큰 소비" 순서라 닉네임 중복 같은 실패에서는 토큰이 남는다. 재설정은 소비를 먼저 한다.
- 로컬에는 SMTP가 없어서 인증 코드를 서버 로그에 남기는 개발 전용 발송기를 썼다. 로컬 프로파일에서만 켜져야 하고, 그 가드를 테스트로 막아 두었다.

#### E. 탈퇴
- 이메일, 닉네임, 카카오 ID가 이미 NULL을 허용하는 유니크 칼럼이라 탈퇴 후 재가입에 별도 마이그레이션이 필요 없었다. NULL은 H2와 PostgreSQL 모두 유니크에서 서로 다른 값으로 취급한다. PostgreSQL 15의 `NULLS NOT DISTINCT`로 바꾸면 깨진다.
- 탈퇴할 때 카카오 연결 해제는 사용자의 카카오 토큰이 서버에 없어서 관리자 키와 대상 ID로 한다. 키가 없으면 건너뛰고, 실패하면 로그만 남기고 탈퇴를 계속한다.
- 탈퇴 이벤트는 커밋 후 동기 발행이고 수신기 예외는 삼킨다. 정리가 누락될 수 있고 재시도 장치가 필요하다(멱등한 정리와 복구 호출).
- 파생 삭제(`deleteByUserId`)는 flush 때 INSERT가 DELETE보다 먼저 나가 같은 값을 다시 넣으면 기본 키 위반이 난다. 벌크 삭제를 쓰고 flush와 clear를 같이 해야 한다.

#### F. 카카오
- 카카오 이메일은 `is_email_valid`와 `is_email_verified`가 모두 참일 때만 쓴다. 아니면 남의 이메일을 선점해 그 사람의 가입을 막을 수 있다.
- 이메일 계정과 자동으로 합치지 않고 USER4093으로 거절한다. 다른 카카오 계정이 쓰는 이메일이면 이메일 없이 가입시킨다.
- 카카오 토큰의 `app_id` 검증이 없다(다른 앱의 토큰을 카카오가 거절하는지 실호출로 확인하지 못했다).
- 실제 카카오 호출과 SDK는 키가 없어서 미검증이고, 개발용 가짜 토큰만 쓴다.

#### G. 사진
- 선언된 형식(Content-Type)과 실제 디코딩을 둘 다 검사해야 한다. 헤더만 보면 가짜 파일이 통과한다. 헤더 크기로 픽셀 수를 먼저 제한하고, 한 번 읽은 뒤 항상 JPEG로 다시 인코딩한다.
- 다시 인코딩하면 EXIF와 함께 회전 정보도 사라져서, 버리기 전에 회전을 픽셀에 반영해야 한다. ICC 색상 정보도 사라져 색이 조금 달라질 수 있다. CMYK JPEG는 디코딩에 실패한다.
- 허용 픽셀 상한이 5천만이면 디코딩 하나에 힙 150~200MB가 들어 동시 업로드로 서버가 멈춘다. 약 1천6백만 픽셀로 낮추고 동시 디코딩 수를 제한해야 한다(수정 중).
- 저장 키는 UUID 난수여야 하고 클라이언트 파일 이름에서 확장자를 가져오면 안 된다.
- 사진 주소 경로는 로그인한 사용자만 받을 수 있고 주소가 추측 불가능해도, 앱의 이미지 로더가 인증 헤더를 붙여야 한다. 헤더 없이 쓰려면 경로를 공개로 풀어야 하고, 그러면 주소 유출이 곧 사진 공개다. 배포(S3)에서는 CDN이나 서명된 주소로 바꿔야 한다.
- 다운로드 경로는 프로파일이 아니라 저장소 설정(`storage.type`)으로 켜지고 기본값이 `local`이다. 배포에서 설정을 빠뜨리면 사진이 서버 디스크에 쌓인다. 기본값을 없애서 설정이 없으면 기동이 실패하게 해야 한다.
- 동시 업로드는 `UPDATE ... WHERE photo_key IS NULL`의 반환값이 0이면 졌다고 판단하고, 진 쪽이 이미 저장한 파일은 지운다. 파일 저장 뒤 DB 커밋이 실패하면 고아 파일이 남아 정리 작업이 필요하다.
- 사진 보너스의 적립 시각은 업로드 시각이다. 자정 직전에 인증하고 자정 후 올리면 보너스는 다음 날 통계에 잡힌다. 활동 일지의 `earnedPoint`는 기본 점수와 보너스의 합이다.
- 캐시 정책: 서버가 사진에 "저장하지 말라"고 주면 앱이 디스크 캐시를 끄므로 목록이 길면 같은 사진을 매번 다시 받는다.
- 투명 PNG는 흰 배경에 그려 JPEG로 바꿔야 한다(아니면 배경이 검게 나옴). 활동 일지 항목에는 첫 방문 여부와 마감 시각이 없어 "사진 추가"를 낙관적으로 보여주고 서버 거절을 문구로 알린다. 서버가 사진 가능 여부와 마감을 내려주면 정확해진다.

#### H. 통계, 랭킹, 연속 참여
- 연속 참여는 한국 시간 `completion_date`의 중복 없는 날짜로 매번 계산한다(오늘이나 어제가 있으면 이어지고 하루라도 빠지면 끊김, 재방문과 같은 날 두 번은 하루). 사용자가 늘면 `currentStreak`, `longestStreak`, `lastActiveDate`를 저장해야 한다. 도착 인증 한 트랜잭션에서 갱신하라는 명세와도 맞는다.
- 랭킹은 도메인 경계 때문에 SQL로 사용자 테이블을 합칠 수 없어서, 기간 집계를 전부 읽고 사용자 도메인에서 걸러낸 뒤 메모리에서 순위를 매긴다. 거른 뒤에 크기를 잘라야 제외된 사용자가 순위를 밀지 않는다. 사용자가 많아지면 캐시나 Redis 정렬 집합이 필요하고, 호출 제한도 필요하다(로그인한 한 명이 반복 호출해도 서버를 압박한다).
- 표준 경쟁 순위(1,2,2,4)라서 공동 2위가 둘이면 시상대 오른쪽 칸에 2위 메달이 한 번 더 나온다. 랭킹에는 커서가 없고 크기만 있다.
- 통계의 `categories`에는 보너스만 받은 카테고리(코드가 빈 값)가 올 수 있다. 도넛에서는 개수 0을 빼고 빈 코드는 "기타"로 보여준다. `totalPoint`는 보너스를 포함하고 `completionCount`는 포함하지 않는다.
- 월간 막대는 28~31칸이라 축 글자를 5일마다만 그린다. "오늘" 판정은 앱의 한국 시간 시계 기준이라 기기와 서버 시계가 어긋나면 하루 틀릴 수 있다.

#### I. 시간과 날짜
- 한국 시간은 `Clock` 빈 하나로 통일하고 `LocalDate.now()`를 인자 없이 쓰지 않는다. JVM 기본 시간대 설정이 `main()`에만 있으면 테스트나 다른 진입점에서 적용되지 않았다.
- 토큰은 `Clock` 기준으로 만료된다. 테스트에서 시각을 하루 뒤로 옮기면 기존 토큰이 모두 401이 된다.
- 서버 시각이 시간대 표기 없는 문자열이라 앱은 앞 16자만 잘라 표시한다. 생성 시각은 팀 저장소 기본 방식이 JVM 시간대로 저장해서 운영이 UTC면 UTC로 저장된다.
- 23:59와 00:01 경계, 월요일 시작 주, 하루 1회 제한을 고정 시계 테스트로 확인했다.

#### J. DB와 마이그레이션
- 팀 저장소의 `ddl-auto=update`를 `validate`와 Flyway로 바꿨다. 팀원 로컬 DB가 이미 `update`로 만들어져 있으면 초기화나 baseline이 필요하다. 엔티티를 추가하는 에이전트는 반드시 같은 번호 구역의 마이그레이션도 넣어야 한다(안 넣으면 기동 실패).
- SQL은 H2(PostgreSQL 모드)와 PostgreSQL 17 양쪽에서 돌도록 표준 문법만 썼지만 PostgreSQL에서는 한 번도 돌려 보지 못했다. 확인할 것: `BOOLEAN` 매핑, `photo_key` 유니크 인덱스가 NULL 여러 행을 허용하는지, 집계 쿼리의 `case when ... then 1L`이 bigint로 해석되는지, 동시 업로드와 동시 인증의 동작, 제약 이름이 예외 메시지로 오는 형태.
- H2는 함수 기반 인덱스를 지원하지 않아 닉네임의 대소문자 구분 없는 유니크를 DB로 막을 수 없다(PostgreSQL에서는 `lower(nickname)` 인덱스). 지금은 앱 검사만 대소문자를 무시해서 동시 가입이면 "Abc"와 "abc"가 둘 다 들어갈 수 있다.
- 마이그레이션에서 테이블을 지우고 다시 만드는 것은 데이터 손실 위험이 있다(V103).
- 하루 1회 제한은 DB 유니크 제약이 최종 방어선이고, 그 위반만 409로 바꿔야 한다. 모든 무결성 위반을 409로 바꾸면 원인이 가려진다.
- 로컬 샘플 데이터가 테스트 DB에 새어 들어가는 문제는 H2 데이터베이스 이름을 분리해서 막았다.
- H2를 배포 산출물에서 분리해야 하고, `local` 설정(고정 사용자, 고정 JWT 키)이 운영에서 켜지지 않게 막아야 한다.

#### K. JSON과 직렬화
- Kotlin의 `isHot`, `isCompleted`, `isFirstVisit`, `isMockLocation`, `isMe` 같은 `is` 접두사 속성은 `@get:JsonProperty`와 `@param:JsonProperty`를 둘 다 붙여야 키가 유지된다. 요청 DTO를 non-null로 두면 필드 누락이 `body` 오류로 나가서 필드 이름이 사라지므로 nullable과 `@field:NotBlank`를 쓴다.
- 앱의 `coerceInputValues`가 서버의 null을 빈 문자열로 바꿔서 가린다. 앱의 `ignoreUnknownKeys`는 서버가 키를 추가해도 런타임에 안 깨지게 하므로, 알림 장치는 계약 테스트뿐이다. 서버는 모르는 요청 키를 거부하지 않는다.
- 앱의 직렬화 설정 `encodeDefaults=false`는 요청 필수 필드에 기본값을 주면 키가 빠진다. 온보딩 수정에서 null은 키 생략(변경 없음), `interests` 빈 배열은 전체 삭제로 구분된다.
- Kotlin 주석 안에 `/auth/**`나 `requests/*.json`처럼 `/*`가 들어가면 중첩 주석으로 읽혀 "Unclosed comment" 컴파일 오류가 난다(세 에이전트가 모두 한 번씩 겪음).
- Jackson 3의 `JsonNode`는 자체 `map` 멤버가 있어 Kotlin의 `map`이 가려진다.

#### L. 앱
- 소스셋: debug 전용 클래스는 `src/debug`에 두고 release에는 같은 이름의 껍데기를 둔다. 공용 `src/test`가 debug 전용 클래스를 참조하면 release 테스트 컴파일이 깨져서, debug 전용 테스트는 `src/testDebug`, release 전용은 `src/testRelease`에 둔다.
- 코드 난독화(R8)를 켜면 직렬화 라이브러리와 서버 통신 라이브러리를 보호하는 규칙이 필요하다. 규칙이 없으면 JSON 필드 이름이 난독화되거나 직렬화기를 못 찾는다. 단위 테스트는 난독화 전 코드를 돌리므로 못 잡아서, 켠 뒤에는 release 빌드로 서버 호출, 재발급, 직렬화를 실제로 돌려 봐야 한다.
- 보안 저장소(EncryptedSharedPreferences)가 깨지면 앱이 시작할 때마다 죽는다. 생성 실패 시 파일과 키를 지우고 빈 저장소로 다시 열어 로그아웃 상태로 복구해야 한다. 라이브러리가 알파 버전(`1.1.0-alpha06`)이다. 백업 제외는 `dataExtractionRules`(12 이상)와 `fullBackupContent`(11 이하) 둘 다 필요하다.
- 온보딩 필요 플래그는 토큰을 저장하기 전에 세팅해야 내비게이션이 올바르게 간다. 시작 때 온보딩 완료를 확인하되 실패해도 진입은 막지 않는다.
- 사진 선택기(Photo Picker)는 저장소 권한이 필요 없다. 카메라 촬영은 파일 공급자 설정이 필요해서 이번에는 만들지 않았다. 안드로이드 8~10 기기는 최근 저장된 위치만 써서 도착 인증에 오래된 위치가 나갈 수 있다.
- 이메일 코드 확인 화면에는 재발송 대기 카운트다운과 남은 시도 횟수가 필요하고, 인증 토큰이 만료되면 이메일 단계로 돌려보내야 한다.

#### M. 개발 방식에서 배운 것
- 에이전트의 보고는 길면 잘린다. 지시에 "최대 N줄, 이미 보낸 것은 반복하지 않기"를 넣고 잘린 뒤에는 이어서 요청하면 된다.
- 에이전트 두 개가 명세 페이지를 한꺼번에 읽다가 600초 무응답으로 멈췄다. "한 번에 하나씩, 자주 커밋하기"를 지시에 넣으면 재개했을 때 작업이 남는다.
- 이 PC는 여유 메모리가 2~3GB여서 Gradle을 여러 개 동시에 돌리면 느려지고, 다른 에이전트의 데몬을 끊는 `--stop`을 쓰면 안 된다. 한 번 데몬이 강제 종료돼 빌드가 실패했는데 코드 문제가 아니었다.
- 이 PC의 줄바꿈 변환(CRLF) 때문에 편집이 조용히 실패할 수 있다. 긴 한글 heredoc은 파싱 오류가 나서 파일은 쓰기 도구로 만들었다. 에이전트가 만든 파일이나 임시 로그가 저장소에 섞일 수 있어 커밋은 파일을 지정해서 한다.
- 각 에이전트의 "git status가 깨끗하다"와 "테스트가 통과했다"는 보고도 합친 뒤 제가 다시 실행해 확인했을 때 어긋난 적이 있었다(앱 계약 테스트의 사용자 준비, 보고 이후의 미커밋 수정).
- 계약 테스트는 서버와 앱의 응답 형식 어긋남을 사람이 아니라 테스트가 잡게 한다. 시연에서 필드 이름 변경, 타입 변경, 키 추가, null 허용 변경이 모두 잡혔고, 요청 검증을 빼면 500이 나는 것도 확인했다.

#### N. 보안 점검 요약(읽기 전용 review, 총 18건: 높음 1, 중간 9, 낮음 8)
서버의 기본기(JWT 검증, 토큰 회전, 인증 코드, 데이터 접근 격리, 인젝션 방어, 사진 처리, 비밀값 관리)는 양호했다. 지적과 처리 상황:
- **높음:** 탈퇴 시 사진과 위치가 지워지지 않음 → 수정 중.
- **수정 중인 중간 이하:** 이메일 코드 시도 횟수의 원자화, 로그인 제한 카운터의 원자화, 사진 디코딩 메모리 상한, Swagger 운영 비공개, 저장소 종류 필수 설정, 에러 로그의 개인정보 제거, 앱의 보안 저장소 복구와 백업 제외.
- **기록만 하는 것(실제로 만들 때 반드시 고칠 것):** 이메일 발송의 IP별과 전역 제한과 이메일 열거 응답 정리, 랭킹 캐시와 호출 제한, 비동기 메일 발송, 계정별 로그인 잠금, refresh token 패밀리와 재사용 탐지와 절대 만료와 기기별 세션, access token 즉시 폐기, 닉네임의 `lower()` 유니크 인덱스, 완료 기록의 404와 403 구분(존재 여부 노출), 키 강도와 `iss/aud/kid`, 도착 인증 사기 방어(기기 증명, 요청 제한, 불가능한 이동 검사), R8.
- 점검에서 검증하지 못한 것: 실제 Redis와 PostgreSQL 경로, 카카오 토큰의 앱 ID 검증, 72바이트가 넘는 비밀번호의 처리, JSON 본문 크기 상한.
