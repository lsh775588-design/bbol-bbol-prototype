# 2단계 보고서: 도착 인증, 포인트, 추천 (팀 저장소 스택) + 앱 화면

- 일자: 2026-11-14
- 서버 작업 위치: `C:\dev\bbolbbol\server`(팀 저장소 복제본), 통합 브랜치 `port/integration`. **팀 저장소(origin)에는 올리지 않았다.**
- 앱 작업 위치: 바깥 저장소 `app/`, 통합 브랜치 `feat/2-integration`(main에는 병합하지 않음)
- 담당(이름표가 있는 에이전트): `completion-point`(도착 인증과 포인트, 리뷰 수정), `recommendations`(추천), `stage2-review`(읽기 전용 검수), `app-stage2`(앱 화면). 오케스트레이터가 확인과 통합.

## 서버: 한 일

### 도착 인증과 포인트 (`completion-point`)
- `POST /places/{placeId}/completions`: HTTP 201. 요청 `lat`, `lng`, `accuracy`, `isMockLocation`. 응답 `completionId`, `placeId`, `placeName`, `isFirstVisit`, `earnedPoint`, `totalPoint`, `completedAt`, `photoBonusPoint`, `photoDeadline`.
- 검사 순서: 장소 없음(PLACE404) → 오늘 이미 인증(COMPLETION409) → 모의 위치(COMPLETION4003) → GPS 정확도 100m 초과(COMPLETION4002) → 인증 반경 밖(COMPLETION4001). 명세에 순서가 없어 정한 가정이다.
- 점수: 첫 방문 100%, 재방문 50%(내림). 장소별 점수가 카테고리 점수를 덮는다. 같은 장소 하루 1회는 한국 시간(`Clock`) 기준이고 DB의 유니크 제약으로도 강제한다.
- 완료 기록과 포인트 내역은 한 트랜잭션이다. 동시 8요청 테스트에서 성공 1건, 409 7건, 500 0건이었다.
- `GET /users/me/points`(총점, 오늘 점수, 인증 횟수), `GET /users/me/point-histories`(커서 페이지네이션, size 기본 20 최대 50, type 필터), `GET /users/me/completions`(활동 일지, 기간과 카테고리 필터, 커서).
- 장소 목록과 상세의 방문 여부, 오늘 인증 여부, 예상 포인트가 실제 값으로 바뀐다(쿼리 2번, N+1 없음).
- 새 테이블: `completions`(V300), `point_histories`(V400). 로컬 데모용 시드는 V920(local 전용).

### 추천 (`recommendations`)
- `GET /places/recommendations`: 뽈뽈 추천(CURATED) 장소만, "안 가본 곳 우선 → 거리순". size 기본 5, 최대 10. 인기 장소(POPULAR)는 3단계 영역이라 확장 지점(`RecommendationSource`)만 만들었다.

### 리뷰 후 수정 (`completion-point`, `port/fix2`)
- 409 범위를 좁혔다: 하루 1회 제한 위반만 COMPLETION409이고, 다른 DB 오류는 원인을 숨기지 않고 로그(개인 정보 없이)를 남긴 뒤 500으로 나간다.
- 쓰이지 않던 임시 방문 상태 클래스(`PlaceholderPlaceUserStateProvider`)를 삭제했다.
- 추천과 도착 인증이 함께 동작하는 통합 테스트를 추가했다(안 가본 곳 → 이전에 간 곳 → 오늘 간 곳 순서).
- 앱이 보내는 위치, 정확도, 모의 위치 값을 서버가 그대로 믿는다는 신뢰 경계를 코드 설명으로 남겼다.
- 커서가 목록 끝을 넘은 경우와 `size` 경계(1, 50, 0, 51) 테스트를 추가했다.

## 앱 (`app-stage2`)
- 장소 상세의 "도착 인증하기": 위치, 정확도, 모의 위치 여부를 보내고 결과(획득 포인트, 총점, 첫 방문)를 보여준다. 둘러보기 모드나 위치 권한이 없으면 비활성화. 오류는 코드별 한국어 문구.
- 내 정보 상단의 포인트 요약, 포인트 내역과 활동 일지 화면(더 보기로 페이지 이어 보기, 로딩과 빈 화면과 오류 상태), 지도 상단의 뽈뽈 추천 목록(카드를 누르면 지도로 돌아가 상세 열림).
- 사진 업로드는 서버에 없어서 만들지 않고 "사진 보너스는 준비 중이에요" 안내만 표시한다.

## review 결과(읽기 전용, `stage2-review`): 조건부 통과
- 높음 등급 결함은 없었다. 명세의 필드, 상태 코드, 에러 코드는 일치했고, 원자성, 동시성, 사용자 데이터 격리, 커서 주입 방어, PostgreSQL 이식성(표준 DDL)에 문제가 없었다.
- review는 파일을 바꾸지 않았다(`git status` 확인).
- 지적 중 3단계 전에 고칠 것(409 범위, 쓰지 않는 임시 클래스, 통합 테스트 부족, 신뢰 경계 기록)은 모두 수정했다. 테스트 부족 지적 중 일부는 이미 있었다(리뷰어가 미검증으로 남긴 것).

## 명세와 다른 점, 가정한 것
- **포인트 합계를 사용자 테이블에 저장하지 않고 포인트 내역의 합으로 계산한다.** 명세는 사용자 테이블에 누적 저장하라고 한다. 응답 값은 같고 합계가 어긋날 위험은 없지만, 내역이 매우 많아지면 느려질 수 있다.
- **연속 참여 일수를 도착 인증과 한 트랜잭션에서 갱신하지 않는다.** 명세에 있지만 3단계(연속 참여 랭킹)에서 완료 기록으로 계산할지 저장할지 정해야 한다.
- 추천 정렬은 명세의 "안 가본 카테고리 우선"이 아니라 "안 가본 장소 우선"이다. 추천 이유 문구는 명세에 규칙이 없어 서버가 정했다. 사용자 위치와 상관없이 추천 장소 전체에서 거리순으로 고른다.
- 재방문 50%는 내림으로 처리했다. 기본 점수가 1점이면 재방문이 0점인 내역이 생긴다(시드에는 해당 없음).
- 검사 순서는 위와 같이 정했다. 이미 인증한 장소는 모의 위치와 정확도 오류보다 먼저 409를 돌려준다.
- 활동 일지의 `earnedPoint`는 기본 점수만 담고, 사진 보너스를 구현하면 합산해야 한다.
- 포인트 내역의 응답 키 `createdAt`의 값은 `earned_at`이다(명세의 키 유지).
- 온보딩 미완료나 닉네임 없는 사용자도 인증을 막지 않는다(쟁점 5 미결정).

## 알아둘 점(보안)
- **앱이 보내는 위치, 정확도, 모의 위치 값을 서버가 그대로 믿는다.** 악의적인 클라이언트가 정확도 0과 장소 좌표를 보내면 어디서든 인증할 수 있다. 요청 횟수 제한과 불가능한 이동 검사도 없다. 명세의 백엔드 참고에 "완벽한 방어는 아님, 과제 범위에는 충분"이라고 적혀 있어 명세 위반은 아니다. 저장된 위치와 정확도로 나중에 이상 징후를 탐지할 수 있다.

## 구현하지 않은 것(쟁점 대기, 3단계 대상이지만 결정이 없어 보류)
사진 업로드와 사진 보너스(쟁점 8), 통계와 랭킹(쟁점 6: 날짜 기준), 이메일 인증 발송과 확인, 비밀번호 재설정(쟁점 2), 토큰 재발급과 로그아웃(쟁점 3), 회원 탈퇴(쟁점 4), 카카오 로그인(쟁점 1, 5), 온보딩 조회와 저장(쟁점 5). 도착 인증 응답은 명세대로 첫 방문에 사진 보너스 50점과 마감 시각을 내려주지만 업로드가 없어 받을 방법이 없다.

## 미검증
- 에뮬레이터 확인과 화면 스크린샷: 사용자가 다른 프로젝트 확인을 위해 에뮬레이터 사용을 중단시켰다. 앱 2단계 화면은 컴파일과 단위 테스트까지만 확인했다(Compose 화면, 위치 취득, 모의 위치 실제 값, 추천에서 지도로 돌아오는 이동).
- PostgreSQL 17과 PostGIS 실연동(Docker 없음). 유니크 제약 이름이 PostgreSQL에서 예외로 오는 방식은 가짜 예외 테스트로만 확인했다.
- Redis 실연동, 카카오 수집 스크립트 실호출.
- 팀 저장소에 올리는 것은 하지 않았다.

## 내가 결정해야 할 것
1. 포인트 합계를 사용자 테이블에 저장할지(명세) 지금처럼 계산할지.
2. 연속 참여 일수를 저장하며 갱신할지, 완료 기록으로 계산할지(3단계).

5. 안드로이드 8~10(API 26~29) 기기의 오래된 위치 문제: 단발 위치 요청으로 고칠지.
6. 포인트 내역의 유형 필터, 활동 일지의 날짜와 카테고리 필터 화면을 넣을지.
7. 에뮬레이터를 다시 쓰는 시점(앱 화면 스크린샷 촬영).
8. 쟁점 2~8의 결정(구현 보류 중인 API 14개).
